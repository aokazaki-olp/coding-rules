**H-1 の詳細（本巡で最も価値が高い）**

§5.5 の ✅ 例は `await using` スコープ内で `return handle.readFile(...)` と `await` を省いている。
`@typescript-eslint/return-await` が発火するが、これは様式の問題ではなく**実バグ**である。

```
規約どおり (return r.slowRead())      → [dispose] 実行 → 失敗: クローズ済みリソースから読もうとした
lint 要求 (return await r.slowRead()) → [dispose] 実行 → 成功: データ
```

`FileHandle` では偶然成功する（Node 内部が fd を先に掴むため）。一般には壊れる。
併せて §5.3 の「`Promise` の直接 `return` — `await` 不要なら省略してよい」は
`using` スコープ内では危険であり、無条件の推奨として書けない。

**H-2 の詳細（唯一の3視点一致）**

§6.2 は `instanceof Error` を禁じ `Error.isError` を要求するが、§6.3 の ✅ 例は
`e instanceof SuppressedError` を使っている。A が `node:vm` の別 context で実測:

```
foreign ctor name         : SuppressedError
instanceof SuppressedError: false   ← §6.2 が警告する誤判定がそのまま発生
Error.isError             : true
```

`Error.isSuppressedError` は存在しない（B が確認）ため、代替手段を規約が示す必要がある。
誤判定すると §6.3 が防ごうとしている「本来の原因の取り落とし」がそのまま起きる。

**H-3 の詳細**

`max-statements-per-line`（ESLint core、非推奨でも削除済みでもない）が違反行のみ検出する。
§8.2 は「機械が守れないので規約文の側で守る」一覧であり、そこに偽の項目があると
各リポジトリは実在するルールを設定しなくなる（§1.2 の「機械に守らせる」方針に逆行）。
